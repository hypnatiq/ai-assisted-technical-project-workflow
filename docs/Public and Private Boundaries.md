# Public and Private Boundaries

## Safe to explain publicly

- The high-level project workflow
- How requirements and evidence are reviewed
- Which validation methods were used
- Sanitized examples and screenshots
- Verified results and documented limits
- Public repository links and published project status

## Kept private

- Complete personalized assistant instructions
- Personal memory and correction history
- Machine-specific configuration and local security state
- Credentials, tokens, sessions, and account information
- Raw packet captures and private endpoint lists
- Unpublished application source and internal project evidence
- Employer, customer, or third-party information that was not approved for release

## Why the difference matters

The public project should show how I think and validate work without exposing the private information or complete configuration needed to recreate my personal assistant environment.

This keeps the portfolio useful while protecting the parts that are personal, sensitive, or still unfinished.
