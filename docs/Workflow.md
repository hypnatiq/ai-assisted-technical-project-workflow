# Workflow

## 1. Define the result

Start with the practical result the project should produce.

Record:

- what needs to work
- who it is for
- what must not change
- what evidence will show that it works
- which actions require approval

## 2. Establish the starting point

Before changing anything, identify the current files, version, configuration, and known behavior.

Keep original files or an approved source when a rollback may be needed.

## 3. Build one testable change

Turn the requirement into the smallest useful change that can be checked. This may be a source edit, a troubleshooting step, a document revision, a screenshot set, or a structured investigation.

## 4. Review the evidence

Use the evidence that fits the work:

- source or regression tests
- rendered document pages
- screenshots of the real interface
- file counts, sizes, and SHA-256 hashes
- packet or connection evidence
- official documentation and source references

Keep the difference between source checks, packaged builds, installation, live behavior, and public release clear.

## 5. Keep failed results

A failed or incomplete test explains what needs to change next. Record the failure, adjustment, new result, and remaining limit.

Do not turn an unfinished result into a success claim.

## 6. Review privacy and public claims

Before sharing anything:

- remove credentials and account information
- remove private addresses and local paths when they are not needed
- use sanitized or synthetic examples when real data should stay private
- confirm that screenshots match the written claim
- state what the evidence does not prove

## 7. Approve the result

I make the final decision about whether the work is ready to use, needs another test, should remain private, or can be published.

AI assistance does not replace that approval.
